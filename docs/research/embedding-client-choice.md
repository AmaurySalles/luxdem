# Replace the client, and probably the model

Use a small custom `Embeddings` subclass over the `ollama` Python package. It calls `/api/embed` in sub-batches and sets `options`, `keep_alive`, `truncate`, a timeout and retries. The default model choice is **bge-m3** (no prefixes, 8K context, strongest French score on MIRACL among sub-1B models). Confirm it with a short in-domain bake-off against snowflake-arctic-embed2 and a nomic baseline that uses the correct prefixes. The current `langchain_community` client sends **one sequential POST per chunk** to the deprecated `/api/embeddings` endpoint. It also silently adds E5 prefixes (`passage: `/`query: `), which nomic was never trained on, so the existing index is off-spec. langchain-ollama 0.1.3 is the only partner package that fits the 0.2 pins. It batches, but it cannot set `num_ctx` or `num_batch`. Those matter because Ollama clamps nomic-embed-text to **2048 tokens**, and bert-family models get capped at 2048 unless `num_batch` is raised. nomic v1.5 is also an English-only model: English uncased vocabulary, accents stripped. You are re-embedding about 90% of the corpus anyway, so changing the model now costs almost nothing extra. Two things are still unknown: how big the gain is on this corpus, and an open Ollama bug that corrupts embeddings of accented text in BERT-derived models. Both must be checked on the laptop before paying for GPU time.

## The community client is slow, off-spec and has no context control

The four options differ more than "batching or not" suggests. langchain-community 0.2.19's `OllamaEmbeddings._embed` loops `requests.post(".../api/embeddings")` once per text. It reuses no session, sets no timeout and has no retry. It prepends `embed_instruction="passage: "` / `query_instruction="query: "` whatever the model ([source](https://github.com/langchain-ai/langchain/blob/langchain-community%3D%3D0.2.19/libs/community/langchain_community/embeddings/ollama.py)). The legacy endpoint returns **unnormalized** vectors and has no `truncate` parameter. `/api/embed` takes a list, L2-normalizes each vector, and **silently truncates by default** ([api.md](https://github.com/ollama/ollama/blob/main/docs/api.md), [routes.go](https://github.com/ollama/ollama/blob/main/server/routes.go)). The only signal that truncation happened is a low `prompt_eval_count` ([#14259](https://github.com/ollama/ollama/issues/14259)). At 100k chunks over a 20–40 ms tunnel, round trips alone cost roughly 35–70 minutes with the community client. That is an estimate, scaled from the earlier GPU-provider research.

| Option | Endpoint / batching | `num_ctx`, `num_batch`, `keep_alive`, `truncate` | Timeout / retry | Fits pins |
|---|---|---|---|---|
| community 0.2.19 (current) | `/api/embeddings`, 1 POST per text | `num_ctx` only; no keep_alive/truncate | none / none | yes |
| langchain-ollama 0.1.3 | `/api/embed`, whole list in 1 POST | **none** (added in 0.3.0, which needs core 0.3) | via `client_kwargs` / none | yes, only 0.1.3 ([PyPI](https://pypi.org/project/langchain-ollama/#history)) |
| subclass over `ollama.Client` | `/api/embed`, your sub-batch size | all, plus `dimensions` | settable / write it | yes |
| raw HTTP `/api/embed` | same | all | write it | yes |

langchain-ollama 0.1.0/0.1.1 ignore `base_url`, and 0.1.2 is yanked, so 0.1.3 is the only usable partner version ([PyPI](https://pypi.org/project/langchain-ollama/0.1.3/)). It sends whatever list it receives as **a single request**. Without `num_batch` it cannot lift the 2048-token cap on bge-m3. A custom subclass is about 30–50 lines and gives full control. It also works as a stopgap: drop it once the app moves to core 0.3+ and langchain-ollama 0.3+. Raw HTTP saves one dependency but means writing the error handling yourself. The `ollama` package already raises typed `ResponseError` and `ConnectionError` and reuses one `httpx.Client`, but its default timeout is **None** ([_client.py](https://github.com/ollama/ollama-python/blob/main/ollama/_client.py)), so set one. The community class has no deprecation warning under the 0.2 pins. The decorator only arrives in langchain-community 0.3.2 ([PyPI](https://pypi.org/project/langchain-community/#history)), so the absence of a warning tells you nothing.

Batching has to happen in two places. langchain-chroma 0.1.4's `add_texts` calls `embed_documents` once for the whole list, then does one `upsert` with no `max_batch_size` splitting ([vectorstores.py @0.1.4](https://github.com/langchain-ai/langchain/blob/langchain-chroma%3D%3D0.1.4/libs/partners/chroma/langchain_chroma/vectorstores.py)). So an oversized `add_documents` call can compute every embedding and then fail at upsert. Slice `add_documents` calls (a few hundred docs each), and sub-batch inside `embed_documents` (32–128 texts per request). On the server, each list item becomes a separate runner call gated by `OLLAMA_NUM_PARALLEL`, which **defaults to 1** ([llama_server.go](https://github.com/ollama/ollama/blob/main/llm/llama_server.go), [faq](https://github.com/ollama/ollama/blob/main/docs/faq.mdx)). On the 3090, set it to 8–16. Context memory scales with `num_ctx × parallel`, which is small for these models (inference).

## Nomic v1.5 is the wrong model for French tables

Prefixes are a property of the model. Nomic v1.5 says the prefix "*must*" be `search_document: ` for chunks and `search_query: ` for queries ([HF card](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5)). Ollama adds nothing. No one has published how much `passage:`/`query:` costs on nomic. The nearest vendor figure is 1–5% retrieval loss when Qwen3 omits its instruction ([Qwen3 card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)). But fixing prefixes does not fix the model. v1.5 is tagged English and uses the `bert-base-uncased` tokenizer (30,522 tokens), which lowercases and strips accents. "Logement", "loyer", "locataire" and "wohnung" are not single tokens ([tokenizer.json](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5/blob/main/tokenizer.json)). Ollama clamps its `num_ctx 8192` to the GGUF's **2048** trained context ([#11214](https://github.com/ollama/ollama/issues/11214), [#13054](https://github.com/ollama/ollama/issues/13054)). So a ~2,400-word merged table, which French WordPiece inflates well beyond 3k tokens, loses its tail. The DECISIONS.md note that the max chunk is "well under the 8192-token embedding limit" is therefore wrong for nomic under Ollama.

Sources: MIRACL from the Nomic v2 paper, all inputs truncated to 512 tokens ([arXiv 2502.07972](https://arxiv.org/html/2502.07972)). CLEF from the [Snowflake card](https://huggingface.co/Snowflake/snowflake-arctic-embed-l-v2.0). MMTEB from the [Qwen3 card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B). Context sizes from the Ollama library pages ([bge-m3](https://ollama.com/library/bge-m3), [arctic2](https://ollama.com/library/snowflake-arctic-embed2), [qwen3](https://ollama.com/library/qwen3-embedding)). The tables were built by different vendors with different setups, so compare within a column only. nomic-v2-moe and granite-embedding are limited to 512 tokens in Ollama, so they are out unless you re-chunk. bge-m3 wins on simplicity: no prefixes, so query and document handling cannot drift apart. It also has the best French MIRACL score. arctic2 is the serious challenger. CLEF, a European-news benchmark, is closer to legislative text than Wikipedia-based MIRACL, and there it beats bge-m3 by 12 points. That gap is big enough to justify the bake-off. One caveat applies to both: on Ollama 0.34.2, bge-m3 with `num_ctx 8192` still stopped at `prompt_eval_count = 2048` until `num_batch` was raised ([#14259 comment](https://github.com/ollama/ollama/issues/14259)). That is a concrete reason to use the custom client over langchain-ollama 0.1.3. Even with 8K, one vector for a 2,400-word table is diluted. Splitting tables with the header repeated is still worth trying later, but it is not required for this run.

## Ollama versions change vectors more than CUDA vs Metal does

The biggest parity risk comes from the Ollama release, not from the GPU. Issue #15609 is open and directly hits a French/German corpus. In BERT-derived embedders on Ollama ≥0.14.0, unrelated words with diacritics reach cosine 0.992, against 0.426 for an ASCII control. The issue bisected a clean break between v0.13.4 and v0.14.0 using a byte-identical blob, and the fix PR is unmerged ([#15609](https://github.com/ollama/ollama/issues/15609)). Its tests used nomic and mxbai. Whether bge-m3 (XLM-R) or arctic2 is affected is **unknown**, so run the issue's probe on the candidate version before anything else. Other releases also changed vectors for the same blob. v0.30.0 made nomic lowercase its input, and the engine switched in v0.13.1, v0.14.0 and v0.30.0 ([releases](https://github.com/ollama/ollama/releases)). The regression in which `truncate:true` still returns "input length exceeds the context length" is also open. It is worse for multilingual text ([#14186](https://github.com/ollama/ollama/issues/14186)). So send `truncate:false`, catch the error, and split or log on the client. Do not rely on silent cuts.

No primary source measures CUDA against Metal cosine for the same model. Expect ≥0.999 rather than bit equality (inference), and test it. Pin the identical Ollama version on both machines. On Linux the install script accepts `OLLAMA_VERSION`. Turn off auto-update on the Mac. Check that the model digest matches in `ollama list`. Record version and digest in the collection metadata. Leave nomic's `num_ctx` at a power of two, because odd values change its output ([#7595](https://github.com/ollama/ollama/issues/7595)).

## Cosine space must be set at creation, and thresholds will move

Chroma defaults to squared `l2`, and the space cannot be changed after creation ([Chroma docs](https://docs.trychroma.com/docs/collections/configure)). `/api/embed` vectors are unit-norm, so l2 and cosine rank identically: ‖a−b‖² = 2 − 2cos. Set cosine explicitly anyway, so a stray unnormalized client cannot silently re-rank results. On langchain-chroma 0.1.4 this is `collection_metadata={"hnsw:space": "cosine"}`. The newer `collection_configuration` argument shown in current docs ([vectorstores.py](https://github.com/langchain-ai/langchain/blob/master/libs/partners/chroma/langchain_chroma/vectorstores.py)) is not available on this version (inference). Confirm the setting on the created collection. Write to a **new collection or directory**. Never mix old (`/api/embeddings`, E5-prefixed) and new vectors. Any hard-coded relevance threshold has to be re-tuned, because the score scale changes with both the space and the model.

Migration cost is small. The code change is one factory function, `get_ollama_embeddings`. Ingest and query both go through it, so the query side follows automatically. Other costs are a 1.2 GB `ollama pull` on the laptop, re-embedding the 73 already-embedded dossiers (trivial), and re-tuning thresholds. Query latency for a sub-600M model on Apple Silicon should stay well under 100 ms (estimate, unmeasured). GPU cost stays trivial: a 3090 on Vast.ai costs $0.16–0.27/h. No reliable nomic or bge-m3 throughput figure exists for a 3090. bge-m3 is about 4× nomic's size and gets longer inputs, so time a 1k-chunk sample before trusting any wall-clock estimate.

## Conclusion

The real choice is not between four clients. It is whether the pipeline controls the embedding request, or a langchain wrapper hides it. Every serious problem found was a hidden default: a prefix the model never saw, a context clamp, a `num_batch` cap, silent truncation, an unbounded timeout. A 40-line client that sets each of these explicitly and logs `prompt_eval_count` turns them into visible decisions. The open diacritics bug matters more than the choice of model. If the pinned Ollama version merges "é" words, no model choice will rescue French retrieval. The probe takes minutes and has to come first.

## Steps

1. Pick one Ollama version and install it on both the Mac and the Vast.ai image. Disable Mac auto-update. Run the #15609 diacritics probe with bge-m3 and arctic2 on that version. If it fails, try another version before going further.
2. Write `OllamaEmbedEmbeddings(Embeddings)` over `ollama.Client(host, timeout=120)`. It sub-batches 64 texts per `client.embed` call with `truncate=False`, `options={"num_ctx": 8192, "num_batch": 8192}` (2048 for nomic) and `keep_alive=-1` for bulk runs or `"30m"` on the laptop. It retries with backoff on connection errors and 5xx, and splits or logs any chunk that exceeds the context. Give it per-model prefix fields (bge-m3: none; arctic2: `query: ` on queries; nomic: `search_document: ` / `search_query: `). Swap it into `get_ollama_embeddings`.
3. Slice `add_documents` calls into a few hundred docs each, and write to a new Chroma directory created with `collection_metadata={"hnsw:space": "cosine"}` plus the model, Ollama version and digest.
4. Run the bake-off on the laptop. Embed a subset of about 30 dossiers plus ONH chunks, including long tables and some German, with bge-m3, arctic2 and nomic with correct prefixes (optionally qwen3-embedding:0.6b). Score 30–50 hand-labelled French and German queries on recall@10 and MRR. Choose a model.
5. Run the parity check. Embed about 200 chunks (accented, German, tables) on the laptop and on a briefly rented 3090 with `OLLAMA_NUM_PARALLEL=8`. Require a minimum cosine ≥0.999, and confirm that `prompt_eval_count` matches the client token counts.
6. On the same rental, time 1k chunks to size the job. Then run the full re-embed, with parsing finished beforehand so the GPU is not idle.
7. Point the query path at the new collection, re-tune any relevance thresholds, update DECISIONS.md (correcting the "8192-token limit" note), and delete the old collection.

Unresolved: whether #15609 affects bge-m3 or arctic2; exact chromadb `max_batch_size`; whether 3090 `-np` batching changes vectors.
